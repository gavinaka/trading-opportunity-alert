# 事件驱动 Taker 工作流

结论：本项目不能使用 Codex cron 自动化轮询候选事件。

## 错误方案

```text
Codex 每分钟启动
→ 检查候选队列
→ 重复拉起窗口 / 任务 / 抓取
→ 造成误触发和进程泛滥
```

这个模型已经被验证为不适合当前需求。

## 正确第一版

```text
TradingView 警报触发
→ Webhook 接收事件
→ 校验密钥、解析字段、脱敏、去重、落盘
→ Telegram 发送“候选已收到｜非交易信号”
→ 用户明确要求 Codex 分析该候选
→ Codex 单次读取候选和只读规则
→ 满足条件才发送正式 Taker 预警
```

早盘人工步骤是工作流的一部分：每天 10:00 前由用户在 TradingView 设置当天关键位置警报，并在 JSON 中写入计划ID、关键位、区间、失效参考和触发场景。

## 数据策略

- 第一版只使用 TradingView 警报传入的数据作为实时触发源。
- 不自动抓取旧报告源。
- 不在 Webhook 进程里调用 Codex 模型。
- 不在 Webhook 进程里发送正式交易预警。
- 原 `Trading-System` 只作为只读规则来源，不作为可写工作流。

## 为什么不接旧报告源

Taker 机会的时间窗口很短。旧报告链路需要多源截图、校验和读图，速度不适合日内吃单预警。除非未来能证明有稳定、低延迟、可验证的行情 API，否则第一版不把旧报告源纳入触发链路。

## Webhook 边界

事件接收器只做四件事：

1. 等待 TradingView POST。
2. 校验密钥和字段。
3. 保存候选事件。
4. 发送候选 Telegram 提醒。

事件接收器禁止做四件事：

1. 禁止创建 Codex 自动化。
2. 禁止轮询候选队列。
3. 禁止自动抓取外部源。
4. 禁止发送正式交易信号。
